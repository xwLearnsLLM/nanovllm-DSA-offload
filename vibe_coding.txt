## 目标

当前目标是让 nano-vllm-ascend 在昇腾 NPU 上高性能运行 DeepSeek V3.2 类模型。

目标模型：

- ModelScope：`xwLearnsLLM/Deepseek-V3.2-Pruned-95B`
- 昇腾机器上的常用本地路径：`/home/models/Deepseek-V3.2-Pruned-95B-BF/`
- BF16
- 用户机器上 TP=4 可以跑，TP=8 也用于性能测试
- 当前只关心 DeepSeek V3.2，不再追求 Qwen、多模态、graph mode 或通用模型支持
- 当前只要求 eager 模式可用
- 关键并行方式：Attention TP、MoE EP
- 关键算子尽量对齐 vllm-ascend 0.19.1，但项目方向是逐步内化到 `nanovllm.ops`，摆脱对 vllm-ascend Python 包和其 OPP 注册路径的依赖

## Attention 路线

### Prefill

DeepSeek V3.2 的 DSA 原始设计是 sparse attention：序列长度大于 2048 时，从历史 token 中选择最多 2048 个重要 token 参与 attention。

由于 `npu_sparse_flash_attention` 在 Nano 集成路径中出现过 core dump，当前 prefill 改为 dense paged MLA：

```python
torch_npu.npu_fused_infer_attention_score(...)
```

当前是 absorb + paged KV cache 形态，典型形状：

- query：`(tokens, local_q_heads, 512)`
- ckv cache：`(num_blocks, block_size=128, 1, 512)`
- query_rope：`(tokens, local_q_heads, 64)`
- kpe cache：`(num_blocks, block_size=128, 1, 64)`

用户做过 SFA vs dense MLA 对比：

- 序列长度 1024：dense MLA 和 sparse reference 几乎一致，`relative_max_error` 约 `0.0016`
- 序列长度 3072：SFA 是 3072 选 2048，dense MLA 是全量计算，`relative_max_error` 约 `0.0403`，mean error 很小

结论：prefill 暂时用 dense MLA 可以接受，性能也不错。

### Decode

当前 decode attention backend：

- 默认：`NANOVLLM_DECODE_ATTENTION_BACKEND=mla`
- `mla`：dense paged MLA，当前工作路径
- `torch`：慢速 PyTorch sparse reference，仍依赖 `npu_lightning_indexer` 的 top-k 结果
- `sfa`：`nanovllm.ops.npu_sparse_flash_attention`，当前会复现 core dump
- 旧开关：`NANOVLLM_ENABLE_NPU_SFA_DECODE=1` 会强制走 SFA decode，只用于复现/调试 crash

当前 decode 性能仍不够好。TP8 short prompts 大致结果：

- decode TPS 约 40 tok/s
- TPOT 约 0.16-0.22 秒
- 目标是 TPOT 降到 0.1 秒以下

观察：`decode_attention_op` 很小，但 `attention_total` 明显更大。因此瓶颈大概率不在 MLA kernel 本身，而在投影、cache 写入、q-up/v-up、o-proj、TP all-reduce 或剩余调度开销。

## 已知问题和坑

### 1. SFA decode core dump

`NANOVLLM_ENABLE_NPU_SFA_DECODE=1` 当前会复现 core dump。正常运行不要打开。

### 2. batched q-up 本地算子 crash

之前 sweep 中设置：

```bash
NANOVLLM_Q_UP_BMM_TRANS_MAX_TOKENS=1024
```

batch=7 时让 q-up 走本地 `batch_matmul_transpose`，触发 AICore MTE write address out of range。代码已保护为只有 `num_tokens == 1` 时才走本地 op。

### 3. Tokenizer 问题

Transformers 5.5.3 加载该模型 tokenizer 时曾遇到：

```text
AttributeError: 'tokenizers.Tokenizer' object has no attribute 'backend_tokenizer'
```

当前 tokenizer 加载路径已经有兜底，example 能跑。

### 4. EOS 影响测试

`example/test.py` 默认 `NANOVLLM_IGNORE_EOS=true`，避免固定 decode 长度测试被 `\n + EOS` 提前截断。

### 5. Scheduler 约束

当前 Nano scheduler 要求：

```text
max_num_batched_tokens >= max_model_len
```

README 命令必须保持这一点。

### 6. KV cache 显存

之前 TP4 OOM 过，后来加了 KV cache block cap：按 `max_model_len/max_num_seqs` 限制分配。现在短 decode TP4 和 TP8 都能跑。

## MoE 当前状态

默认：

```bash
NANOVLLM_MOE_BACKEND=grouped
```

Grouped MoE 路径使用：

- `moe_gating_top_k`
- `npu_moe_init_routing_v2`
- `npu_grouped_matmul`
- `npu_moe_token_unpermute`

从 per-expert Python loop 改成 grouped matmul 后，MoE 时延明显下降。

`expert_tokens` 当前保留算子原始 dtype，不再 cast 到 int64。用户日志显示这条路径更快且可跑。

仍保留：

```bash
NANOVLLM_MOE_BACKEND=loop
```

作为调试/对照回退。

## 下一步建议

1. 在昇腾机器上跑新增的细粒度 decode timing。
2. 判断 `attention_total` 主要耗在哪个字段：
   - `q_b`
   - `q_up`
   - `v_up`
   - `o_proj`
   - `attention_gap`
3. 如果 `o_proj` 最大，优先调查 TP all-reduce，考虑通信融合、延迟 all_reduce 或减少同步。
4. 如果 `q_b/q_up/v_up` 最大，考虑小 batch decode 专用投影算子或融合算子。
5. 如果 `attention_gap` 最大，继续细拆 timing，查 Python/runtime dispatch 开销。
6. 长期仍要修 SFA decode core dump，让 decode 回到 sparse attention。

## 2026-05-25：runlog7/runlog8 细粒度 timing 结论

用户运行了两组命令：

- `runlog7.txt`：`NANOVLLM_DECODE_LAYER_TIMING_SYNC=0`，低扰动看趋势
- `runlog8.txt`：`NANOVLLM_DECODE_LAYER_TIMING_SYNC=1`，同步精确量少数层

结果概要：

- `runlog7.txt`：decode TPS 约 `41.41 tok/s`
- `runlog8.txt`：decode TPS 约 `38.00 tok/s`
- `decode_attention_op` 不是主瓶颈，整体平均占比约 `7-9%`
- `q_b` 很小，整体平均占比约 `4%`
- `q_up/v_up` 也不大，各自约 `5%`
- `kv_rope` 是稳定大头：
  - sync=0 整体约 `0.70 ms/layer`，约 `39% attention_total`
  - sync=1 整体约 `0.79 ms/layer`，约 `24% attention_total`
- `o_proj` 很可疑：
  - sync=0 平均不算特别大，但出现过 rank0/layer60 `o_proj=4.296 ms` 的尖刺
  - sync=1 整体约 `0.80 ms/layer`，约 `24% attention_total`
  - `o_proj` 包含 RowParallelLinear 的 TP `all_reduce`，因此大概率暴露出 TP 通信/同步开销
- `attention_gap` 在 sync=1 下约 `0.46 ms/layer`，可能包含未细拆的 Python/runtime 调度、同步测量扰动和小段代码开销

当前判断：

1. MLA kernel 本身不是 decode 瓶颈。
2. 投影里的 `q_b/q_up/v_up` 不是首要问题。
3. 下一步优先看：
   - `kv_rope`：拆分 RMSNorm、rotary、split/squeeze 的开销，考虑 decode 专用轻量路径
   - `o_proj`：拆出 `F.linear` 和 TP `all_reduce`，确认是不是通信主导
4. 如果 `o_proj all_reduce` 确认为主因，再考虑通信优化、延迟/融合 all_reduce，或参考 vllm-ascend 的 TP attention 输出处理。

## 2026-05-25：runlog9/runlog10 细拆结果

用户运行两组命令：

- `runlog9.txt`：`NANOVLLM_DECODE_LAYER_TIMING_SYNC=0`
- `runlog10.txt`：`NANOVLLM_DECODE_LAYER_TIMING_SYNC=1`

统计结论：

- `sync=0` 更适合看趋势，decode TPOT 约 `0.16-0.18s`。
- `sync=1` 会明显扰动流水，decode TPOT 约 `0.20-0.23s`，并把 `o_all_reduce` 等同步相关字段显著放大。
- `sync=0` 下，三层采样整体平均：
  - `attention_total` 约 `1.63 ms/layer`
  - `kv_rope` 约 `0.67 ms/layer`
  - `rotary` 约 `0.47 ms/layer`
  - `kv_norm` 约 `0.16 ms/layer`
  - `decode_attention_op` 约 `0.16 ms/layer`
  - `o_proj` 约 `0.14 ms/layer`
  - `o_all_reduce` 约 `0.09 ms/layer`
  - `moe_total` 约 `0.56 ms/layer`
- 真正稳定的大头是 `rotary + kv_norm` 和 MoE；MLA attention 算子本体不是瓶颈。
- `sync=1` 下 `o_all_reduce` 约 `0.88 ms/layer`，但低扰动下只有约 `0.09 ms/layer`，说明同步计时会严重放大通信等待，不应直接按 sync=1 的 `o_all_reduce` 做优化判断。

和 vllm-ascend 0.19 对照：

- vllm-ascend 的 MLA/SFA decode-only 小 token 路径会尝试走 `MLAPO`：
  - 代码位置：`vllm_ascend/attention/mla_v1.py`
  - 条件类似：`enable_mlapo and num_decode_tokens <= 1024 and num_prefills == 0`
  - 调用：`DeviceOperator.mla_preprocess_only_decode(...)`
  - 核心算子：`torch.ops._C_ascend.mla_preprocess`
- `mla_preprocess` 会把 decode 前处理融合到一个算子里，包括 qkv-a、q norm、q-up、kv norm、RoPE、写 KV cache 等。
- 当前 nano-vllm 仍把这些步骤拆成多个小算子，所以 `rotary`/`kv_norm` 的启动和访存开销会被逐层放大。
- 本仓库 `csrc/nanovllm_ascend_ops/mla_preprocess` 里已经有 MLAPO 源码，但 `nanovllm/ops/__init__.py` 和 `csrc/nanovllm_ascend_ops/nanovllm_ops.cpp` 当前还没有把 `mla_preprocess` 暴露给 Python。

下一步最像 vllm-ascend 的优化路线：

1. 把 `mla_preprocess` 绑定到 `nanovllm.ops.mla_preprocess`。
2. 在 decode-only 路径加入一个 `NANOVLLM_DECODE_MLAPO=1` 开关，先只用于 decode。
3. 用当前拆分路径做参考，写一个 `ut_ops/probe_mla_preprocess.py` 对比：
   - `ql_nope`
   - `q_pe`
   - `ckv_cache`
   - `kpe_cache`
   - 可选 `q_c`
4. 对齐后再集成到 `deepseek_v32.py`，预计优先降低 `rotary + kv_norm + q_up/cache` 这一段。

## 2026-05-25：全面对照 vllm / vllm-ascend 的 decode pipeline

用户提醒：不能只看 `rotary`，需要全面对照 vllm 和 vllm-ascend，因为 vllm-ascend 可能把多个步骤融合在一起。

源码对照后的结论：

- vLLM 原生 DeepSeek MLA 已经把 `q_a_proj` 和 `kv_a_proj_with_mqa` 打包成 `fused_qkv_a_proj`；nano-vllm 当前也已经在权重准备阶段做了类似的 `wd_qkv` 合并，所以 `qkv_a` 不是当前最大差距。
- vllm-ascend MLA/SFA decode-only 路径会优先尝试 `MLAPO`：
  - `MLAPO_MAX_SUPPORTED_TOKENS = 1024`
  - 条件大致是 `enable_mlapo and decode_tokens <= 1024 and num_prefills == 0`
  - 调用 `DeviceOperator.mla_preprocess_only_decode(...)`
  - 底层算子是 `torch.ops._C_ascend.mla_preprocess`
- `mla_preprocess` 不是单纯替换 rotary，而是融合一整段 decode 前处理：qkv-a、q RMSNorm、q-up、kv RMSNorm、RoPE、KV cache 写入，并输出 decode 用的 `q_nope/q_pe` 等。
- vllm-ascend 在非 MLAPO 路径也不是普通 PyTorch 拆分：
  - KV 侧用 `torch_npu.npu_kv_rmsnorm_rope_cache(...)` 融合 KV RMSNorm、K RoPE、cache 写入。
  - Q RoPE 用 `torch_npu.npu_interleave_rope(...)`。
  - dense MLA decode 用 `torch_npu.npu_fused_infer_attention_score_v2(...)`，并带 workspace / graph 参数路径。
  - v-up 用 `torch_npu.npu_transpose_batchmatmul(...)` 或 `_C_ascend.batch_matmul_transpose(...)`。
- DeepSeek V3.2 DSA/SFA 路径里，vllm-ascend 还会使用 `npu_lightning_indexer`、`npu_sparse_flash_attention`，并在 SFA 路径里同样尝试 MLAPO。
- MoE 侧，vllm-ascend 不是简单 per-rank local expert loop，而是有 `AscendFusedMoE`、`build_fused_experts_input`、`moe_comm_method.fused_experts(...)`、`ALLTOALL/MC2/FUSED_MC2`、dispatch/combine、weight prefetch 等整套路径。

因此当前 nano-vllm 和 vllm-ascend 的主要差距不是某一个 `rotary` 算子，而是：

1. Attention decode 前处理没有走 `mla_preprocess` / `npu_kv_rmsnorm_rope_cache` 这种融合路径。
2. Decode 当前用 dense MLA 替代 SFA，规避了 SFA core dump，但也没有和 vllm-ascend DSA/SFA 路径完全对齐。
3. MoE 已做了一些局部优化，但还没对齐 vllm-ascend 的 fused MoE + 通信/dispatch/combine 路径。

后续优化优先级：

1. 先暴露并验证 `nanovllm.ops.mla_preprocess`，这是最直接对齐 vllm-ascend 的 decode attention 前处理优化。
2. 如果 MLAPO 接口一时不好对齐，可以先做中间态：引入 `npu_kv_rmsnorm_rope_cache` 和 `npu_interleave_rope`，减少当前 `kv_norm + rotary + cache` 的小算子拆分。
3. 接着继续拆 MoE timing，并逐步参考 vllm-ascend 的 fused MoE / MC2 / alltoall 路线。
4. SFA decode core dump 是最终必须回来的问题；dense MLA decode 只是现阶段性能和可运行性的折中。

## 2026-05-25：MLAPO probe 首轮结果与修正

用户在昇腾机器上成功运行 `ut_ops/probe_mla_preprocess.py`，说明 `nanovllm.ops.mla_preprocess` 的 Python 绑定和 C++/AscendC 编译产物已经能正常调用。

首轮结果：

- `tokens=7`：算子平均约 `0.37 ms`，但 `ql_nope/q_pe/ckv_cache/kpe_cache` 相对误差都很大。
- `tokens=128`：算子平均约 `0.25 ms`，误差同样很大。

这不是 BF16 舍入误差。继续对照 vllm-ascend 0.19 后发现关键原因：

- BF16 no-quant 的 `mla_preprocess` kernel 对 `wdqkv` 和 `wuq` 使用的是 `DataFormat::NZ`。
- vllm-ascend 在 `mla_v1.py/sfa_v1.py` 中会先做：
  - `trans_rope_weight(...)`
  - `transdata(weight, block_size=(16, 32)).unsqueeze(0).contiguous()`
  - `torch_npu.npu_format_cast(..., 29)`
- 之前 probe 直接把普通 ND contiguous `[out, in]` 权重传给 MLAPO，所以 kernel 按 NZ 格式读错了权重，连不涉及 RoPE 的 `ckv_cache` 也会大幅偏离。

已修正 `ut_ops/probe_mla_preprocess.py`：

- 增加 `trans_rope_weight`。
- 增加 vllm-ascend 同款 `transdata`。
- 增加 `to_mlapo_nz_weight`，在 NPU 上用 `torch_npu.npu_format_cast(..., 29)` 转成 MLAPO 期望的 NZ 权重。
- reference 继续用普通 ND 权重，算子输入用 NZ 权重。

这次只改 Python probe，不需要重新编译 C++。下一步让用户直接重新跑第 41 条两个 probe 命令即可。

## 2026-05-25：runlog11，NZ 权重后 MLAPO 仍未对齐

  - `MLAPO_BENCH avg_ms=0.204061`
  - 误差仍然大，`ckv_cache mean_abs=1.13019`。

结论：

- NZ 权重之后速度更像一个可用的小融合算子，但精度没有对齐。
- 这说明问题不只是普通 ND 权重被 MLAPO 当 NZ 读。
- vllm-ascend 0.19 中 MLAPO 实际只在 W8A8/MXFP8 量化路径启用；未量化 BF16 模型会关闭 MLAPO。因此本仓库现在使用的 BF16 `quant_mode=no_quant` kernel 可能不是 vllm-ascend 主路径，不能假设它一定正确。

已继续增强 `ut_ops/probe_mla_preprocess.py`：

- 增加 `--quant-mode`，可测试 `no_quant` 与 `per_tensor_quant_asymm`。
- 增加 `--no-format-cast`，可跳过 `torch_npu.npu_format_cast(..., 29)`，只使用显式 `transdata` 后的存储。
- 增加 `ckv_cache_valid` 和 `kpe_cache_valid`，只比较 slotmapping 实际写入的 cache 行，避免 padding 行稀释误差。

已在 `README.md` 增加第 42 条诊断命令：

1. `--init-scale 0`：全零输入，验证基础写出是否干净。
2. `--no-format-cast`：隔离 internal format cast 是否影响。
3. `--quant-mode per_tensor_quant_asymm`：尝试 vllm-ascend 量化路径使用的 tiling key。

## 2026-05-25：runlog12，定位 BF16 no-quant MLAPO 权重分块问题

用户运行第 42 条诊断命令，结果在 `runlog/runlog12.txt`。

结果：

- `--init-scale 0` 全零输入完全对齐：所有 `MLAPO_DIFF` 都是 0。
  - 说明 Python 绑定、输出写回、slotmapping/cache 基础写出逻辑大体是通的。
- `--no-format-cast` 结果和默认路径几乎完全一样。
  - 说明误差不是 `torch_npu.npu_format_cast(..., 29)` 本身造成的。
- `--quant-mode per_tensor_quant_asymm` 直接出现 `1e9` 级别误差。
  - BF16 权重硬走量化 tiling key 缺少量化参数，这条路径不成立。

新的关键判断：

- 之前 probe 给 BF16 no-quant MLAPO 权重使用了 vllm-ascend W8A8 量化路径里的 `transdata(..., block_size=(16, 32))`。
- 但 BF16 no-quant kernel 的 NZ 读权重逻辑使用 16 宽 C0，也就是应使用 `(16, 16)`。
- 这能解释为什么 NZ 权重后仍然大误差：权重虽然是 NZ 形状，但物理分块宽度错了。

已修改 `ut_ops/probe_mla_preprocess.py`：

- 新增 `--weight-block-cols`，默认 `16`。
- BF16 no-quant 默认使用 `transdata(..., block_size=(16, 16))`。
- 如果需要复现实验，可以显式设置 `--weight-block-cols 32`。

已更新 `README.md` 第 41/42 条：

- 第 41 条默认命令现在代表 BF16 no-quant 正确分块尝试。
- 第 42 条第三个命令改成 `--weight-block-cols 32`，作为对照诊断，不再推荐 `per_tensor_quant_asymm`。
